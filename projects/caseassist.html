CaseAssist

In development

A Salesforce project for claims triage in financial services: structured intake, rule based risk classification that already works, and an Agentforce agent layer still in progress. CaseAssist is a personal project built to learn in public. It is not a client deployment, and this page separates what is implemented from what is simulated and what is still an idea.

View the GitHub repository Back to projects

The problem

Claims and service requests arrive unstructured: free text, missing fields, unclear urgency. A person reads each one, decides what it is and where it goes, and that manual triage is slow and inconsistent. The cost is not only time. Inconsistent triage means similar cases are handled differently, and urgent cases wait behind routine ones. CaseAssist builds the structured foundation first, a real data model and real Apex services, and then explores how much of the first pass AI assistance can honestly carry, with a person approving anything that matters.

The implemented data model

Two custom objects carry the design. A claim always hangs off a policy, and the classifier reads both before it decides anything.

Policy__c

  • Status__c: the policy state the classifier checks first
→

Claim__c

  • Related_Policy__c: lookup to Policy__c
  • Description__c: what happened, in the claimant words
  • Incident_Date__c: when it happened
  • Estimated_Amount__c: the estimated claim amount
  • Claim_Status__c: starts at New on creation

Run the real classification rules

This demonstration runs the same rules, in the same order, as ClaimRiskClassifier in the repository. It is a web run of implemented Apex logic, not a mockup and not AI. Set a policy status and an estimated amount, then run the classifier.

The classifier itself, from the repository:

public static String classifyRisk(Claim__c claim, Policy__c relatedPolicy) { if (relatedPolicy.Status__c != 'Active') { return 'High'; } if (claim.Estimated_Amount__c == null) { return 'Medium'; } if (claim.Estimated_Amount__c >= 10000) { return 'High'; } if (claim.Estimated_Amount__c >= 2000) { return 'Medium'; } return 'Low'; }

The class comment in the repository says plainly what this is: a rule based first version, where a production version would incorporate an AI scoring model using historical claims data. That future model is a plan, not a feature, and the Agentforce layer above is where the AI exploration actually lives.

Guided walkthrough

This walkthrough demonstrates the intended workflow using a sample claim written for this page. It is a simulation of the design. It is not connected to a live Salesforce org, and no real claim data is used. Steps 1 and 2 rest on the implemented model and services; step 3 is the layer still in development; step 4 is the design concept.

Step 1 of 4

1. A claim arrives

A policyholder reports water damage from a burst pipe and asks what happens next. The message is free text: no claim type, no severity, no policy reference in a standard place.

Status: intake structure is part of the completed data model.

2. Intake creates a structured case

ClaimCreationService creates a Claim__c record linked to the policy, with the incident date and estimated amount captured as fields and Claim_Status__c set to New, so the record can be routed, reported on, and audited.

Status: data model and core Apex services are complete.

3. Classification, then agent assistance

Today, ClaimRiskClassifier assigns the risk level using the rules you can run above. The Agentforce layer in development would then read the case and propose a category, an urgency, and a draft next step for the handler, with the suggestion and its basis visible rather than silent.

Status: the classifier is implemented Apex. The Agentforce agent layer is in development; its part of this stage is simulated.

4. A person approves escalation

Nothing escalates on the strength of a suggestion alone. A handler reviews the proposal and approves, adjusts, or rejects it, and the case carries that decision forward.

Status: design concept, part of the intended workflow.

What I am learning from this project

Building the data model first changed every later decision for the better: services and any future agent layer read from real fields instead of free text, and every suggestion can be checked against the record. The project is also teaching me the discipline of status honesty. A designed feature is not a working feature, and saying so plainly is part of the engineering.

What remains

The Agentforce agent layer, the designed escalation workflow, and fuller test coverage as the agent layer matures. Agentforce and Data 360 are technologies I am currently learning, and they are labeled that way everywhere on this site.
